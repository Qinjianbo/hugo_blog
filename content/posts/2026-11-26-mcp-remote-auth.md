前四篇的 Server 都在本机：客户端把它当子进程拉起来，关掉客户端它就退出。这一篇把 Server 挪到远端——它常驻在另一台机器上，你只拿到一个网址。连接方式变了，鉴权也从“没有”变成必须认真对待的事。

## 一、两种跑法，先分清

|  | 本地 Server（stdio） | 远程 Server（HTTP） |
| --- | --- | --- |
| 谁启动它 | 客户端拉起子进程 | 它自己常驻，你连它的网址 |
| 凭据在哪 | 配置文件和环境变量里 | 授权后拿到的令牌里 |
| 谁能用 | 只有这台机器 | 有网址和授权的人 |
| 典型场景 | filesystem、fetch 这类本机工具 | 团队服务、云端 API、ChatGPT 接的 Server |

第 3 篇提过，ChatGPT 网页版只能连远程 Server，原因就在这张表里：它在云端，拉不起你机器上的子进程。远程化解决的是“Server 不在手边”的问题，代价是多一整套鉴权。

## 二、Streamable HTTP：一个端点

远程连接走 Streamable HTTP，形状很简单：**所有请求都 POST 到同一个端点**（通常是 `/mcp`），请求体就是前几篇见过的 JSON-RPC。Server 可以直接回一段 JSON，也可以把响应开成一条 SSE 流边算边推。早期的 HTTP+SSE 是两个端点（一发一收分开），2026 年 7 月 28 日的现行规范已把它列为废弃，十二个月内陆续退场，新 Server 不要再用它。

现行规范还改了一件大事：**连接不再有会话**。老版本（2025 年 11 月 25 日版及更早）连上之后先做一次 `initialize` 握手，Server 发一个会话 ID（`Mcp-Session-Id` 头），之后每个请求都带上它，Server 靠它认人。新版把握手和会话 ID 一起取消：每个请求自己带齐信息——协议版本、客户端身份、能力清单都写在请求体的 `_meta` 里，方法名和工具名还抄一份到 HTTP 头（`Mcp-Method`、`Mcp-Name`），网关不用拆 JSON 就能路由和限流。想先看 Server 有什么能力，随时发一个 `server/discover` 就行，它只是普通请求，不再是开场白。

好处是部署变简单：请求互不依赖，负载均衡后面随便哪台机器接都行，不用共享会话存储。**但现实要说清**：2026 年 11 月的实测里，真正讲新版协议的 Server 只有约 0.2%，市面上绝大多数远程 Server 还是老版的握手加会话。主流 SDK 两边都支持，客户端连上去会自动对齐版本——你作为使用者基本无感，写 Server 的人才需要分清自己在跟谁说话。

## 三、鉴权：OAuth 2.1 一条龙

远程 Server 面向网络，必须先回答“你是谁、你能干什么”。规范的答案是 OAuth 2.1，角色分工是：MCP Server 是**资源服务器**，只验令牌；发令牌的是一个独立的**授权服务器**。一次完整的连接是这样走的：

1. 客户端不带令牌发请求，Server 回 `401`，并在 `WWW-Authenticate` 头里指出自己的资源元数据地址（`resource_metadata`）。
2. 客户端取这份元数据（RFC 9728），里面写着该去哪个授权服务器登录。
3. 客户端去授权服务器走授权码流程（带 PKCE），你在浏览器里登录、看清它要的权限范围、点同意。
4. 授权请求里带一个资源指示参数（RFC 8707），写明“这张令牌是发给这个 MCP Server 的”。拿到的令牌因此被绑死在目标 Server 上，偷去别的 Server 用不了。
5. 之后每个请求带 `Authorization: Bearer <令牌>`，Server 逐个验签名、签发者、受众和权限范围。

两条硬规矩值得记住。**令牌不能透传**：Server 收到你的令牌，不能原样转手去调它背后的 API，它得用自己的凭据、按自己的权限去调。**受众必须对得上**：令牌不是发给自己的，Server 必须拒绝，这正是资源指示参数存在的意义。

也有更简单的路：不少 Server 用静态 API Key，客户端在请求头里带上就行，不走浏览器授权。省事，但 Key 等于一把万能钥匙——没有权限范围、没有过期、泄漏了就是全开。个人自用可以，团队和对外服务老老实实用 OAuth。

## 四、客户端怎么自报家门

OAuth 有个前提：授权服务器得先认识客户端，知道它叫什么、授权完往哪跳。MCP 的客户端和授权服务器通常素不相识，谁来登记？

老办法是动态客户端注册（DCR，RFC 7591）：客户端运行时自己 POST 一份资料过去，授权服务器当场发一个 `client_id`。问题在于它只登记、不核实——成千上万个 AI 应用在同一台授权服务器上自助注册，留下一堆没人能担保的记录，注册机制被当成了身份机制用。

新版规范把 DCR 列为废弃，换成**客户端 ID 元数据文档**（CIMD）：客户端在自己域名下放一个 JSON 文件，文件网址本身就是 `client_id`。授权服务器拿到网址后自己去抓文件、核对内容（文件里写的 ID 必须和网址一字不差），再按自己的信任策略决定认不认。身份因此绑在域名上，没人点头之前，授权服务器那边连一条记录都不会有。客户端的尝试顺序也写死了：预先登记的凭据优先，其次 CIMD，再次 DCR，最后才轮到让你手工填。DCR 还能用，废弃有十二个月的最低窗口，最早也要到 2027 年 7 月 28 日那版规范才可能真正移除。

对你来说这一节的结论只有一句：**这些都由客户端自动完成**。你点连接、浏览器里登录授权，剩下的不用管。只有当某个 Server 让你手工粘贴 `client_id` 和密钥时，那是走到最后一条兜底路了，粘贴前多确认一遍来源。

## 五、自己把 Server 放到远端

第 7 篇会动手写 Server，这里先把远程化的底线说清：

- **走 HTTPS**。令牌在请求头里跑，明文 HTTP 等于把钥匙写在明信片上。
- **进程只听本机，前面放反向代理**。跟本地大模型系列里 vLLM 的教训一样：服务进程绑 `127.0.0.1`，由 Caddy、Nginx 这类代理对外并终止 TLS，不要把进程端口直接暴露到公网。
- **校验 Origin 头**。浏览器里打开的恶意网页也能向本机地址发请求（DNS 重绑定就是钻这个空子），Server 要拒绝来路不明的 Origin。
- **鉴权默认开，权限给最小**。只读的工具给只读范围；能写、能删的工具单独把关，不要一张令牌全通。
- **无状态能帮你扩容**。新版协议请求互不依赖，多开几个实例挂在负载均衡后面即可，不用为会话做粘性路由。

## 练习：20 分钟，看一遍鉴权全程

1. 打开 MCP Inspector，选 Streamable HTTP，填一个你第 3 篇接过的远程 Server 地址，连接，看它列出的 Tools。
2. 打开终端，对同一地址发一个不带令牌的请求：`curl -i -X POST <地址> -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'`。在返回的 `401` 里找到 `resource_metadata` 地址，浏览器打开它，认一认 `authorization_servers` 指向哪。
3. 回到客户端重新连接，在浏览器授权页上停一下：看清它要的权限范围再点同意。连上之后想一想：这张令牌是发给谁的、能干什么、什么时候过期。

## 安全提示

远程 Server 的工具在别人机器上跑，你的令牌决定了它能以你的身份干什么。**授权页上的权限范围要逐项看**，只要读的就别给写的；**令牌和 API Key 只发给它们该去的 Server**，受众绑定防的是令牌被转手滥用，但你自己把 Key 粘进不明配置文件，什么绑定都救不了。第 6 篇会把远程场景的风险面一次讲透。
